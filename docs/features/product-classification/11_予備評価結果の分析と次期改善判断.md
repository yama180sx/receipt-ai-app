# 商品単位AI自動分類 — 評価結果の分析と次期改善判断

対象 Issue: [#565 Issue #114-2](https://github.com/yama180sx/receipt-ai-app/issues/565)<br>
判断日: 2026-08-02（JST）<br>
入力資料: [10_実レシート予備評価記録.md](./10_実レシート予備評価記録.md)

## 1. 判断の目的

実レシート再評価で得た基準値をもとに、分類品質を改善する次の実装単位を決定する。本Issueでは未合意のアプリケーション実装、標準分類ルールの個別追加、閾値変更は行わない。

## 2. 入力結果

| 観点 | 再評価結果 | 判断への影響 |
|---|---:|---|
| レシート数 / 明細数 | 9件 / 57件 | 初期基準値として記録できたが、商品・店舗の多様性は限定的 |
| 商品分類対象明細 | 54件 | 分類率を比較する母数を確定できた |
| 標準辞書の自動確定率 | 46.30%（25 / 54） | 飲料・スナックの初期ルールは実データで利用された |
| 未分類率 | 53.70%（29 / 54） | 未分類の原因を商品分類対象外と辞書・ProductType不足に切り分ける必要がある |
| 要確認 / 類似候補 | 0件 / 0件 | 類似検索の閾値を判断できない |
| 世帯辞書・確定履歴の利用 | 0件 | 再利用率を判断できない |
| 分類AI実行 | 0件 | 自動確定基準、コスト、処理時間、修正率を判断できない |
| 値引き・アプリ適用の未分類行 | 5件 | 商品名として扱うべきでない行が未分類率に混在している |

## 3. 次期改善の意思決定

| 論点 | 判断 | 根拠 | 後続対応 |
|---|---|---|---|
| 値引き・アプリ適用行 | **採用** | 未分類29件のうち5件を占め、辞書追加・AI判断では解決しない。商品分類の対象外にすれば、要確認一覧と指標を商品明細へ限定できる | [#601 Issue #114-8](https://github.com/yama180sx/receipt-ai-app/issues/601) |
| 標準分類ルールの個別追加 | **運用で継続** | 初期ルールは25件を自動確定した。一方、未分類には値引き行・初期ProductType外の商品も混在しており、今回の集計だけでは一律の追加対象を確定できない | 管理画面で、商品種別が人手で確認できたキーワードだけを追加する。実装Issueは作らない |
| ProductType追加・初期対象範囲拡大 | **保留** | 未分類名だけでは、必要な商品種別体系・利用頻度・誤分類リスクを判断できない | 日常利用で同種の商品と修正履歴を収集してから再評価する |
| 類似検索の閾値 | **保留** | 類似候補・`needs_review`が0件で、閾値を比較する観測値がない | 類似候補が発生した時点で候補順位・修正結果を評価する |
| AI自動確定基準 | **保留** | `ProductClassificationAiRun`が0件で、信頼度・コスト・処理時間・修正率を評価できない | 実行ログが蓄積した時点で評価する。provider接続診断結果は採用根拠に含めない |

## 4. #601 の実装前提

値引き・アプリ適用行の除外は、レシート明細・金額・家計簿集計を削除または変更しない。商品種別分類だけを対象外（`not_applicable`）にする設計とし、判定条件、既存明細への扱い、DB変更の要否は #601 で実装前に確定する。

## 5. 継続観測

日常利用で追加データが得られた時点で、次を同じ評価記録へ追記する。

1. 世帯辞書に登録済みOCR商品名の再登場と自動再利用
2. 標準分類ルールの追加後における分類率・誤分類・手動修正
3. `needs_review`、類似候補、分類AI実行の候補・信頼度・コスト・処理時間
4. 未分類明細における、初期ProductType不足と標準ルール不足の区別

追加の実装を採用する場合は、判断根拠と対象を明示した別Issueへ分離する。

## 6. Issue #565 の完了判断

再評価結果から、採用する実装を #601 として分離し、それ以外を根拠付きで運用継続または保留とした。したがって #565 の完了条件を満たす。
