# 商品単位AI自動分類 — AI・システム責任分界と分類処理フロー

対象 Issue: [#539 Issue #107](https://github.com/yama180sx/receipt-ai-app/issues/539)

## 1. 基本原則

レシート画像のOCR解析と商品分類は別の責務である。分類のために画像を再送せず、既存情報で解決できない明細だけをテキストでまとめて分類AIへ送る。

## 2. 責任分界

| 担当 | 責務 |
|---|---|
| システム | 画像保存、OCR呼び出し、正規化、履歴・辞書・類似候補の検索、AI呼び出し条件判定、AI出力検証、保存、集計、アクセス制御 |
| 画像解析AI | レシート画像から店舗名、日付、明細名、金額、数量を構造化して抽出 |
| 分類AI | OCR商品名の意味理解、表記揺れの解釈、候補内の `ProductType` 選択、信頼度の返却 |

分類AIは、カテゴリ・商品種別・辞書を新規作成せず、渡された候補のIDからのみ選択する。

## 3. 分類処理

```text
OCR商品名の正規化
↓
Category を決定（標準カテゴリまたは手動設定）
↓
商品種別の対象外カテゴリか
 ├─ はい: ProductType = null, status = not_applicable
 └─ いいえ
     ↓
世帯の確定履歴で完全一致
↓
世帯別辞書で完全一致
↓
標準辞書で完全一致
↓
初期商品種別の範囲外か
 ├─ はい: ProductType = null, status = outside_initial_scope
 └─ いいえ
     ↓
類似検索（Phase 3）
↓
未解決の明細だけを分類AIへ一括送信（Phase 4）
↓
classified / needs_review / unclassified
```

完全一致の優先順位は、確定履歴 > 世帯別辞書 > 標準辞書とする。

## 4. 分類AIの入出力契約

### 入力

- 明細識別子
- OCR商品名と正規化済み商品名
- 必要な補助情報（例: 店舗名）
- 選択可能な `ProductType` のIDと名称

### 出力

- 明細識別子
- `productTypeId` または `null`
- `confidence`: `high` / `medium` / `low`

候補外ID、重複明細、形式不正のJSON、`null`は、システム側で自動確定しない。

## 5. 信頼度と保存

| 条件 | 保存結果 |
|---|---|
| 履歴・辞書の完全一致 | `classified`、対応する分類元、`high` 相当 |
| AI が候補内IDを `high` で返す | 自動確定。分類元 `ai` と信頼度を保存 |
| 類似候補またはAI `medium` / `low` | `needs_review`。候補は保持してよい |
| AIが判定不能、候補外、形式不正 | `unclassified` |

AIの自己申告だけを信頼せず、候補IDの検証・JSONスキーマ検証・実運用での修正率評価を必須とする。

## 6. コストと安全性

- Phase 1 と Phase 2 は分類AIを呼ばない。
- Phase 4 以降も、未解決明細だけをバッチで送る。
- 画像解析用の `RECEIPT_ANALYSIS` と分類用プロンプトは別に管理する。
- 分類AIの利用量は、モデル、入力・出力トークン、対象明細数、結果状態を記録できるようにする。
- 外部AI障害時は、レシート保存を阻害せず、対象明細を `needs_review` または `unclassified` とする。
