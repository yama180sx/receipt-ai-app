# 商品単位AI自動分類 — 実装計画・段階導入方針

対象 Issue: [#539 Issue #107](https://github.com/yama180sx/receipt-ai-app/issues/539)

## 1. 方針

本 Issue は仕様策定のみを扱う。以下のPhaseは、すべて別の実装Issueとして作成・実施する。設計変更が必要になった場合は、実装を先行せず本機能仕様とADRを更新する。

## 2. Phase 分割

| Phase | 実装範囲 | 主な完了条件 |
|---|---|---|
| 1 | 新データモデル、固定標準マスタ、`ProductMaster`廃止、データ初期化、完全一致分類 | 辞書・確定履歴の優先順位、状態・分類元の保存、世帯分離、既存集計の継続 |
| 2 | 商品種別の確認・修正UI、確定履歴、世帯別辞書、修正履歴 | 修正範囲を選べ、世帯内だけに安全に再利用できる |
| 3 | `pg_trgm`類似候補検索 | 類似候補を提示できる。自動確定には使わない。Issue #58と検索基盤を共有する |
| 4 | 分類AI | 未解決明細だけを候補制約付きで分類し、失敗しても保存を阻害しない |
| 5 | 要確認一覧、階層カテゴリ・商品種別統計、辞書管理導線 | 未確認明細を運用でき、商品種別単位の集計ができる |
| 6 | 実レシート評価と改善判断 | 精度、未分類率、修正率、AI呼び出し率、コストを評価し、次の辞書拡張を決める |

## 3. Phase 1 の詳細

### 含めるもの

- 共通標準カテゴリ、`ProductType`、標準辞書のシード
- 世帯別確定履歴・辞書・別名・修正履歴の基礎モデル
- `Item`のCategory、ProductType、状態、分類元、信頼度
- 完全一致による分類
- `ProductMaster`依存の削除
- 開発環境でのバックアップ、初期化、検証後のstable適用手順

### 含めないもの

- `pg_trgm`類似検索
- 分類AI
- 専用の要確認一覧UI
- 商品種別・階層カテゴリの統計UI
- 標準辞書の管理UI

## 4. 評価とテスト

### Phase 1 の必須検証

- 確定履歴 > 世帯別辞書 > 標準辞書の順で完全一致が決まる。
- 別世帯の履歴・辞書・修正は参照されない。
- 全結果に分類状態・分類元・信頼度が残る。
- 未分類でもレシートを保存できる。
- 既存のカテゴリ集計・レシート編集が破綻しない。

### 実運用で記録する基準値

- 辞書完全一致率
- 商品種別未分類率
- ユーザー修正率
- 要確認件数
- Phase 4以降はAI呼び出し率、AI修正率、トークンコスト、処理時間

数値目標は、Phase 1でテスト用実レシートの基準値を取得した後に設定する。

## 5. Issue #58 との関係

Issue #58は、履歴検索のAPI・UIを目的とするため維持する。Phase 3は`pg_trgm`の拡張、正規化列、インデックス、Repositoryなどの共有基盤を実装する。履歴検索API・UIはIssue #58で完結させる。

## 6. 後続Issue作成時の共通チェック

- 本機能仕様・ADRとの整合を確認する。
- OpenAPI変更があれば OpenAPI を先に更新する。
- 全世帯データに対するテナント分離を検証する。
- Geminiはモックを用い、実OCRは手動チェックリストで確認する。
- 破壊的な初期化は、対象・バックアップ・復元・承認をIssue本文とPRに明記する。
