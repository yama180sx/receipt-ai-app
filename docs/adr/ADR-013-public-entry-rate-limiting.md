# ADR-013: 公開入口は明示した信頼境界でレート制限する

## Status

Accepted

関連: [Issue #118-1-3](https://github.com/yama180sx/receipt-ai-app/issues/743)、[Issue #118-1](https://github.com/yama180sx/receipt-ai-app/issues/632)

## Context

限定公開でも、ログイン、招待コード確認、TOTP、画像アップロードはインターネット経由で反復試行・資源消費の対象になる。画像アップロードは特に、メモリ受信・画像変換・外部AIキュー投入を伴う。

リバースプロキシ配下では、クライアントIPを得るために`X-Forwarded-For`を参照する場合がある。しかし、アプリが任意の同ヘッダーを無条件に信頼すると、攻撃者は識別子を偽装して制限を迂回できる。

## Decision

- 単一VM・単一backendプロセスの公開初期は、backendのメモリ内固定ウィンドウで入口を制限する。
- `resolve-family`は15分30回/IP、ログインは15分10回/IP、ログイン前メンバー列挙は15分20回/IPに制限する。
- TOTP設定開始・確認・無効化は15分10回/ログインメンバーID+IP、画像アップロードは15分20回/ログインメンバーID+IPに制限する。
- 制限超過時は、入力値・招待コード・アカウント存在を返さず、`429`、`RATE_LIMITED`、`Retry-After`だけを返す。
- アップロード制限はMulterによるmultipart本文受信より前に配置する。
- `TRUST_PROXY_HOPS`の既定値は`0`とし、`X-Forwarded-For`を信頼しない。公開用の既知リバースプロキシを設置した後だけ、経路に一致する1または2をroot所有の非機密設定へ明示する。
- メモリ内状態はbackend再起動で失われる。複数backendプロセスまたは複数VMへ拡張する時点で、共有レート制限ストアまたはリバースプロキシ/WAFの制限へ置き換える。

## Consequences

### Positive

- 認証試行・招待コード列挙・TOTP総当たり・アップロードによる資源消費を初期公開の前に抑制できる。
- プロキシを未設定の環境では、偽装可能な転送ヘッダーに依存しない。
- アップロード本文を受ける前に拒否できる。

### Trade-offs

- 同一IPを共有する家族・組織ネットワークでは、短時間の大量操作が同じ制限枠を共有する。
- backend再起動は制限カウンターをリセットする。認可・TOTP・AI予算の防御を置き換えるものではない。
- 公開プロキシの構成変更時は、`TRUST_PROXY_HOPS`と実際のhop数を必ず同時にレビューする。
